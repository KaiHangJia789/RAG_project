# PostgreSQL 与 Redis 实战

## 连接池管理

数据库连接是昂贵资源。建立一条 TCP 连接加上认证握手通常需要几十毫秒，如果每个请求都新建连接，高并发下数据库会先被连接开销压垮。

连接池预先建立若干连接并复用。asyncpg 的 `create_pool` 接受 `min_size` 和 `max_size` 控制池的大小，`command_timeout` 控制单条命令的超时。

池大小的经验公式是 `max_size ≈ CPU 核数 × 2 + 磁盘数`，但这个公式针对的是磁盘 IO 密集型负载。实际应该从较小值开始（如 min=2, max=10），观察连接等待时间再调整。

一个必须注意的点：连接池中的连接绑定在创建它的**事件循环**上。跨事件循环使用同一条连接会失败，且报错信息通常很晦涩。这个限制在多线程脚本或与其他框架混用时容易踩到。

## 事务与原子性

跨表操作必须放进事务。asyncpg 的事务上下文管理器在正常退出时提交、异常时回滚：

```python
async with db.transaction() as conn:
    await repo.insert(conn, data)
    await repo.delete(conn, other_id)
```

关键约定是**连接由上层注入**。Repository 层的方法接收 `conn` 参数而不是自己获取连接，这样同一个事务里的多个操作才能共享同一条连接。如果 Repository 自己从池里取连接，每个操作都在独立的事务里，原子性无从谈起。

事务中要避免长时间等待外部调用。在事务里调用外部 API（如嵌入服务）会长时间持有连接和锁，高并发时迅速耗尽连接池。正确做法是先在事务外完成外部调用，再开启事务写库。

## 索引设计

**B-tree 索引**是默认类型，适合等值查询和范围查询。复合索引的列顺序至关重要：`(user_id, created_at)` 能加速"某用户的文档按时间排序"，而 `(created_at, user_id)` 不能。

**部分索引**只索引满足条件的行，体积更小。例如只索引非空值：`CREATE INDEX ... WHERE embedding IS NOT NULL`。

**GIN 索引**配合 `pg_trgm` 扩展支持模糊匹配。`CREATE INDEX ... USING gin (filename gin_trgm_ops)` 可以让 `ILIKE '%关键词%'` 这种前后都带通配符的查询走索引，否则只能全表扫描。

**唯一约束**既是数据完整性保障也是索引。设计时要考虑业务语义是否会变化——一个曾经成立的唯一约束，在需求变化后可能变成阻塞。

## 分页方案的选择

**OFFSET 分页**（`LIMIT 20 OFFSET 1000`）实现简单但有个致命缺陷：数据库必须扫描并丢弃前 1000 行才能返回结果。页码越大越慢，深分页时响应时间呈线性增长。

**Keyset 分页**（游标分页）用排序键作为游标。查询形如：

```sql
SELECT * FROM documents
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 21
```

永远只扫描 `page_size + 1` 行（多取一条用于判断是否还有下一页），不随页码增长而变慢。

游标需要编码传给客户端。通常把排序键序列化成 JSON 再做 base64，客户端原样回传。

代价是 Keyset 分页不支持跳页——用户只能"下一页"不能直接跳到第 5 页。对信息流类界面这不是问题，对需要精确跳页的场景则不合适。

## 枚举类型与数据库迁移

PostgreSQL 支持自定义枚举类型。用枚举而不是字符串列的好处是数据库层面就能防止非法值写入。

代价是枚举类型的修改比较麻烦——新增枚举值需要 `ALTER TYPE ... ADD VALUE`，而删除或重命名枚举值在旧版本中几乎不可行。

迁移脚本必须**幂等**。用 `CREATE TABLE IF NOT EXISTS`、`ADD COLUMN IF NOT EXISTS`、`DROP CONSTRAINT IF EXISTS` 等写法，让脚本可以安全地重复执行。

条件性 DDL（比如"扩展存在时才创建索引"）要包在 `DO $$ ... EXCEPTION WHEN others THEN RAISE NOTICE ...` 块里，让失败降级为提示而不是中断整个迁移。

**修改约束时必须把 DROP 和 ADD 放在同一个事务里**，否则中间态会出现"表没有唯一约束"的窗口，并发写入可能插入重复数据。

修改已有列时顺序固定为：加列（可空）→ 回填数据 → 设默认值 → 设 NOT NULL。直接对含 NULL 行的表加 NOT NULL 约束会失败。

## 缓存模式

**Cache-Aside** 是最常用的缓存模式：读请求先查缓存，命中则返回；未命中则查数据库，把结果写回缓存再返回。写请求先写数据库，然后**删除**缓存（而不是更新缓存）。

为什么写操作是删缓存而不是更新缓存？因为并发更新会乱序。两个请求先后更新数据库，但写缓存的顺序可能相反，导致缓存里是旧值。删除操作是幂等的，不存在这个问题。

**缓存穿透**指查询不存在的数据，缓存永远不命中，请求全部落到数据库。对策是缓存空值——查询未命中时也写一条带短过期时间的空值标记。

**缓存雪崩**指大量缓存同时过期，请求瞬间全部打到数据库。对策是给过期时间加随机抖动：`ttl = base_ttl + random(0, base_ttl * 0.1)`。

**缓存击穿**指某个热点键过期瞬间，大量并发请求同时去查数据库。对策是加互斥锁——只让一个请求去查库并回写，其余请求短暂等待。

## 互斥锁的正确实现

用 Redis 实现互斥锁要处理几个细节。

`SET key value NX EX seconds` 是原子操作：仅当键不存在时设置，并附带过期时间。返回值判断是否获取成功。

**必须设置过期时间**。不设过期的话，持锁进程崩溃后锁永远不释放，所有请求死等。

锁的值应该是唯一标识（如 UUID）。释放锁时要先校验值再删除，否则可能误删别人的锁——A 持锁超时释放，B 拿到锁，此时 A 的释放操作会删掉 B 的锁。校验和删除需要用 Lua 脚本保证原子性。

**降级策略必须明确**。等待锁超时后应该怎么办？直接返回错误？回退到直接查库？返回陈旧数据？这个决策要在代码里显式表达，而不是让异常传播。通常在读多写少的缓存场景，等待超时后回退到查库是可接受的降级。

## Windows 环境注意事项

Redis 官方不支持 Windows。可用的替代方案有：微软的旧版移植（最高 5.0.14）、WSL 中运行、或者 Docker 容器。

使用旧版 Redis 客户端时要注意协议版本。Redis 6 引入的 RESP3 协议需要 `HELLO` 命令，而 Redis 5 不支持该命令。Python 的 redis 库默认可能使用 RESP3，连接 Redis 5 时会报 `unknown command HELLO`。解决方式是显式指定 `protocol=2`。

Windows 下的 PostgreSQL 数据目录受权限保护，普通用户无法直接读取。要查看数据目录位置，可以通过服务的启动参数（`pg_ctl -D <路径>`）或注册表获取。

## 常见坑

**外键约束与硬编码 ID**：`documents.user_id` 指向 `users` 表时，如果代码里硬编码某个用户 UUID，换库后种子数据重新生成了不同的 UUID，插入就会撞外键约束。正确做法是按业务主键（用户名）查询，而不是硬编码代理键。

**DSN 与特殊字符**：数据库密码含 `@`、`:` 等字符时，拼接成 URL 形式的 DSN 会解析错误。用字典形式传参（`host=..., password=...`）可以彻底避免这个问题。

**连接数耗尽**：忘记释放连接、或者在事务里做耗时操作，都会导致连接池耗尽。表现为请求挂起直到超时。监控连接池的等待队列长度可以提前发现。

**缓存与数据库不一致**：缓存失效失败时，读请求会返回陈旧数据。要接受这个现实并设计兜底——短 TTL 是最后一道防线。
