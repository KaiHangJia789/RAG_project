# LLM 应用开发与效果评估

## Prompt 模板化

把 prompt 当作代码资产管理，而不是散落在业务逻辑里的字符串拼接。

基本做法是定义模板类，包含名称、说明、system 文本和 user 模板，用 `str.format` 做占位符替换：

```python
class PromptTemplate(BaseModel):
    name: str
    description: str
    system: str
    user_template: str

    def render(self, **kwargs) -> tuple[str, str]:
        return self.system, self.user_template.format(**kwargs)
```

一个重要的实现细节：**system 通常不做格式化**。如果 system 文本里含有花括号（比如示例 JSON），对它做 format 会抛 KeyError。只格式化 user 模板是更安全的选择。

模板集中注册在一个字典里，按名称索引。这带来三个好处：模板可以被测试覆盖（遍历注册表验证每个模板都能渲染）、可以按名称在配置里切换（用于 A/B 对比）、新增模板不会影响既有代码。

新增模板时要注意**占位符的兼容性**。如果有一个测试遍历所有模板并用固定的参数字典渲染，那么任何使用新占位符的模板都会让这个测试失败。解决方案要么是让测试用超集参数，要么是把不同用途的模板分到不同的注册表。

## 推理模型的特殊处理

DeepSeek V4 Pro 这类推理模型会在正式回答前生成一段"思考内容"（reasoning content）。这段内容对调试很有价值，但有个工程陷阱：

**多轮对话时必须把 reasoning_content 原样回传**，否则 API 会返回 400 错误。实现要点是在把 assistant 消息转换回 API 格式时，只在 reasoning_content 非空时才写入该字段，避免给不支持的场景传空值。

```python
def to_openai_dict(self) -> dict:
    d = {"role": self.role, "content": self.content}
    if self.reasoning_content is not None:
        d["reasoning_content"] = self.reasoning_content
    return d
```

思考模式的开关通过扩展参数传递，不同提供商的字段名不同。DeepSeek 用 `extra_body={"thinking": {"type": "enabled"}}`。

**思考模式与采样参数的冲突**：推理模型开启思考时，temperature 等采样参数会被忽略甚至报错。因此传 temperature 前应该确认思考模式已关闭。

**成本控制的关键洞察**：对判官、分类、抽取这类任务，关掉思考模式比降低 temperature 对稳定性的贡献更大，而且能让调用快 5 到 10 倍。长链路的评估脚本如果不关思考，50 道题可能要跑数小时。

## LLM-as-Judge 评估方法

用大语言模型给另一个模型的输出打分，是当前 RAG 评估的主流方法。它的核心优势是不需要人工标注参考答案就能评估忠实度这类主观指标。

设计判官 prompt 有几个关键原则。

**强制输出 JSON**。自然语言的评分结果难以程序化解析。要求模型输出结构化 JSON（如 `{"score": 0.8, "reason": "..."}`），配合 `response_format={"type": "json_object"}` 参数提高合规率。注意这个参数要求 prompt 里必须出现字面量 "json"，否则部分提供商会报错。

**给出明确的反例**。光说"判断是否相关"不够，模型会倾向于宽松。必须写明边界情况：话题相关但没有给出具体结论的算不相关；信息矛盾算不相关；数字、日期、名称不一致算不相关。反例写得越具体，判官的一致性越高。

**批量判定而非逐条判定**。如果一次调用只判断一条断言，50 道题每题 8 条断言就是 400 次调用。改成一次调用传入全部断言、返回判定数组，调用量降到 50 次。这是评估成本能否承受的关键设计。

**过滤 markdown 围栏**。即使要求"只输出 JSON"，模型仍可能包在 ` ```json ` 里。解析前要剥掉围栏，解析失败时重试一次。

## 四个核心指标的精确口径

**Faithfulness（忠实度）**采用两步法。第一步把答案拆解为原子断言列表——每条断言只包含一个可独立判断真伪的事实，保留具体数字和条件，忽略过渡语和引用标记。第二步批量判断每条断言能否由上下文支持。得分等于被支持断言数除以断言总数。

边界处理：如果答案是拒答，忠实度记为 1.0（拒答不包含事实断言，天然忠实）。如果断言数为零且非拒答，也记为 1.0，但要单独统计这类"退化答案"的数量。如果判官返回的判定数少于断言数，缺失的按"不支持"处理，并标记该次判定格式异常。

**Answer Relevance（答案相关性）**衡量答案是否切题，**不参考上下文**，因此与忠实度正交。

有两种实现路线。一是让判官直接打 0 到 1 分；二是让模型根据答案反推 3 个问题，再计算反推问题与原问题的嵌入相似度均值。后者的优势是确定性（给定答案和嵌入模型，结果完全可复现，方差为零），且跨运行可比；前者方差较大（同一答案重跑可能有 ±0.2 的波动），但更直接。实践中可以两者都跑，用相关系数交叉验证。

**Context Precision（上下文精确率）**评价检索排序质量，采用 rank-weighted average precision：

```
precision@k = (前 k 个位置中相关文档数) / k
ContextPrecision = Σ(precision@k × 相关_k) / 相关文档总数
```

举例：相关性序列 [1, 0, 1, 0, 0] 时，分母是 2，分子是 1×1 + 0 + 0.667×1 = 1.667，结果为 0.833。分母为零（检索结果全部不相关）时记 0 分。

**幻觉率（Hallucination Rate）**是答案级的二值指标：答案中存在至少一条无支撑断言即视为"含幻觉"。幻觉率等于含幻觉的答案数除以有事实断言的答案总数。

它与忠实度的关系是互补而非取反。忠实度是断言级的连续量，会被长答案稀释——一个 20 条断言的答案里有 1 条无支撑，忠实度仍有 0.95；而幻觉率按答案计数，同样的答案会被算作 100% 含幻觉。两个指标一起看，才能同时掌握"平均质量"和"个体风险"。

分母要排除拒答和零断言的答案，因为这两类不可能有幻觉，计入会稀释指标。

## 零成本的确定性指标

有两类指标完全不需要调用模型，应该优先使用。

**基于标注来源的检索指标**。如果评测集标注了每道题的参考来源文档，就能算出：

- `hit_rate@k`：top_k 结果中是否包含标注来源的文档。这是最直观的召回指标。
- `context_precision_by_source`：top_k 中来自标注来源的比例，即精确率。
- `MRR`（平均倒数排名）：第一个命中标注来源的位置的倒数，衡量排序质量。

这三个指标的优点是零成本、完全确定、可跨运行比较。**调参时应该以它们为主要信号，把 LLM 判官的评分作为旁证**。如果两者结论矛盾，说明要么判官不可靠，要么标注有问题——这个矛盾本身就很有价值。

**引用有效性**。解析答案中所有 `[n]` 标记，检查编号是否落在有效范围内。越界率能抓到"编造引用编号"这类幻觉。这是纯正则的，零成本，但判官抓不到——判官只看语义，不看编号是否真实存在。

## 参数调优的方法论

RAG 系统有多个可调参数：块大小、块重叠、检索的 top_k、相似度阈值、最终上下文条数。

**不要做全网格搜索**。5 个参数各取 3 个值就是 243 种组合，每种组合跑 50 道题，成本不可承受。正确做法是分阶段：

第一阶段固定其他参数，单独扫 top_k（如 3、5、10、20），观察召回类指标的变化。通常在某个点之后 recall 饱和而 precision 下降，那个拐点就是最优值。

第二阶段在最优 top_k 下扫相似度阈值。方法是画出可回答问题与不可回答问题的相似度分布，取两条分布之间的谷底。**阈值绝不能拍脑袋**——不同嵌入模型的相似度分布差异极大，某个模型上合理的 0.5 在另一个模型上可能导致全部拒答。

第三阶段在最优 (top_k, 阈值) 下对比不同切分策略。

## 评估集的设计

评测集的质量决定了评估结论的有效性。

**问题必须与语料对齐**。每道题的答案必须真实存在于语料中，且要标注出处（文档名、章节）。如果答案不在语料里，测出来的低分反映的是评测集的问题而非系统的问题。有个简单的自检方法：只用标注的来源文档构造查询，看命中率是否接近 100%。低于这个值说明标注或语料有问题。

**必须包含负样本**。即"语料中确实没有答案"的问题，用于测试拒答能力。没有负样本就无法评估拒答机制，而拒答是 RAG 可信度的关键。负样本的比例建议在 15% 到 20%。

**语料需要刻意设计干扰项**。如果语料里每个主题只有一篇文档、彼此毫无关联，那么检索任务过于简单，任何策略都能得高分，对比实验没有区分度。应该在语料中加入大量"话题相邻但不含答案"的内容，才能真正测出排序质量。

**判官与 prompt 的版本必须记录**。换了判官模型或修改了判官 prompt，历史分数就不再有可比性。报告里必须写明版本，缓存键也必须包含版本号。

## 缓存与可复现性

评估脚本的判官调用应该加缓存。缓存键由判官模型、prompt 版本和输入内容哈希组成，值存原始 JSON 响应。

缓存的价值在于：修改脚本 bug 后重跑，判官调用全部命中缓存，几乎零成本；参数扫描时同一 (问题, 片段) 组合的判定天然复用。

缓存文件应当纳入版本控制，它同时承担了"让报告可复现"的职责——任何人拿到代码和缓存，都能复现出相同的分数。

## 常见坑

**判官 prompt 混进业务模板注册表**：如果有一个测试遍历所有模板并用固定参数渲染，新加的判官模板会因缺少占位符而让测试失败。判官 prompt 应该独立注册。

**评测时忘记关思考模式**：单次调用从 3 秒变成 30 秒，50 道题乘多个配置会跑到天亮，还容易触发限流。

**并发度过高导致限流**：评估框架的并发默认值可能高达 50。50 路并发乘以每题多次调用，瞬间数百个在途请求，必然被限流。应该显式设为 2 到 3。

**在错误的位置取评测样本**：评测框架内部对样本的访问方式可能因来源不同而异（本地传入的是字典，从 API 取回的是对象）。写一个兼容两者的取值函数可以避免"本地能跑、换数据集就崩"。
