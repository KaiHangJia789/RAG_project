# 向量检索与 Embedding 技术

## 嵌入向量的本质

嵌入（Embedding）是把离散符号映射到连续向量空间的技术。文本经过嵌入模型处理后变成一个定长浮点数组，语义相近的文本在向量空间中的距离也相近。

这种"语义距离"的性质是向量检索的基础。关键词检索要求问题和文档包含相同的词，而向量检索不要求——"怎样入门写代码"和"如何学习编程"字面上没有一个共同的关键词，但它们的向量会非常接近。

向量的维度由模型决定。常见的中文嵌入模型维度有 768、1024、1536、2048 等。维度越高表达能力越强，但存储和计算成本也线性增长。阿里云百炼的 qwen3.7-text-embedding-flash 输出 1024 维向量。

## 相似度度量

衡量两个向量有多相似，常用的有三种度量：

**余弦相似度（Cosine Similarity）**计算两个向量夹角的余弦值，取值区间 [-1, 1]。它只关心方向不关心长度，因此不受文本长短影响。这是文本检索中最常用的度量。

**内积（Inner Product）**计算两个向量对应分量乘积之和。它与余弦相似度的关系是：当两个向量都已做 L2 归一化（长度为 1）时，内积恒等于余弦相似度。

**欧氏距离（L2 Distance）**计算向量空间中的直线距离。它与余弦相似度单调相关，但对向量长度敏感。

这个等价关系有重要的工程价值：很多向量索引库（如 FAISS）对归一化向量做内积检索的速度远快于直接算余弦，所以实践中的标准做法是——**入库前对向量做 L2 归一化，检索时同样归一化查询向量，然后直接用内积索引**。数学上得到的结果与余弦相似度完全一致。

## FAISS 索引类型

FAISS（Facebook AI Similarity Search）是最常用的向量检索库。它提供多种索引结构，核心权衡是速度与精度的取舍。

**IndexFlatIP / IndexFlatL2**是最基础的暴力检索索引。它遍历所有向量计算距离，结果绝对精确，但耗时随向量总数线性增长。十万条以内、要求高精度的场景直接用它即可。

**IndexIVFFlat**是倒排文件索引。它先用聚类把向量空间划分为若干桶，检索时只搜索查询向量最近的几个桶。速度提升显著，代价是可能漏掉边界上的近邻。需要先训练聚类中心，检索时通过 nprobe 参数控制搜索多少个桶——nprobe 越大越精确也越慢。

**IndexHNSWFlat**是基于图的近似索引。它构建多层邻近图，检索时在图上做贪心搜索。查询速度极快，但内存占用高，且构建索引耗时较长。

**IndexIVFPQ**在倒排索引基础上加入乘积量化压缩。它把向量切分成若干子段，每段用聚类中心编号表示，内存占用可降低到原始大小的几十分之一。代价是精度损失明显，通常需要配合重排序使用。

选择原则：数据量小于十万用 IndexFlat；十万到千万用 IndexIVFFlat；内存受限且能接受精度损失用 IndexIVFPQ；追求极致查询速度用 IndexHNSWFlat。

## 归一化实践

在 FAISS 中实现余弦检索的标准写法分三步。

第一步，写入时归一化。把所有待索引向量组成矩阵，调用 `faiss.normalize_L2(matrix)` 原地归一化。

第二步，查询时归一化。查询向量同样要归一化，这一步极易遗漏——漏掉的话检索结果不会报错，只是变得毫无意义。

第三步，用 IndexFlatIP 检索。归一化后的内积结果就是余弦相似度，取值 [0, 1]（对非负向量而言）。

需要自定义 id 时用 IndexIDMap 包装：`faiss.IndexIDMap(faiss.IndexFlatIP(dim))`，添加时用 `add_with_ids(vectors, ids)`。这里有一个隐蔽的陷阱：**add_with_ids 对重复 id 不会报错**，它只是追加一条新记录。结果是索引中存在两条不同向量共享同一个 id，检索时返回重复 id 挤占结果名额。所以写入前必须自己检查 id 是否已存在。

## 向量数据库 vs 专用索引库

选型时常在"向量数据库"和"专用索引库"之间纠结，两者定位不同。

**pgvector** 是 PostgreSQL 的扩展，把向量作为一列存储。优势是能在一个事务里同时操作向量和业务数据，支持 SQL 过滤（比如"只在这个用户的文档里检索"），运维成本低——已有的 PostgreSQL 就能用。劣势是性能不如专用库，且需要安装扩展。

**FAISS** 是纯索引库，只管向量不管存储。优势是性能极强、索引类型丰富。劣势是它**没有持久化语义**——索引是进程内状态，需要自己负责落盘和加载；元数据（向量对应的原文是什么）要另外维护；多进程部署时每个进程各持一份索引，无法共享。

**Milvus / Qdrant / Weaviate** 是完整的向量数据库产品。它们把索引、存储、元数据、分布式都封装好了，支持水平扩展。代价是引入一个新的有状态服务，运维复杂度上升。

选型建议：十万级以下、已有 PostgreSQL，用 pgvector 最省心。追求极致性能、数据量在单机可承载范围内，用 FAISS。千万级以上或需要分布式，用专业向量数据库。

如果选了 FAISS 又要存元数据，常见做法是**旁挂一份 sidecar 元数据文件**：向量存 FAISS，chunk 文本、文件名、页码存 JSON 或数据库。检索时先查 FAISS 拿到 id，再用 id 回查元数据。这样做的额外好处是检索路径不依赖数据库查询，单测可以完整覆盖。

## 批量与限流

嵌入 API 通常有单次请求的文本条数上限。工程上必须做分批：把待向量化的文本列表按固定大小（如每批 50 条）切片，逐批调用 API。

分批之外还需要重试。网络抖动是常态，瞬时失败应该自动重试而非直接报错。但要注意区分错误类型：**维度不匹配这类配置错误重试没有意义**，应该在重试逻辑之前就抛出去，否则会白白重试三次再失败，掩盖真正的问题。

维度校验是另一个必要的防护。嵌入模型返回的向量维度如果与配置不符，FAISS 写入时不会报错（只要所有向量维度一致），但检索结果会完全错乱。所以每批返回后都应该逐条检查维度，不匹配立即抛异常。

## 常见坑

**中文字符串的路径问题**：FAISS 的 C++ 底层用 `fopen` 做文件 IO，在 Windows 中文路径下会失败。绕开方式是改用 Python 的 `serialize_index` 把索引序列化成字节，再用 Python 的文件对象写盘。

**空索引检索**：向量数为零时调用 search 会返回无效 id（-1）。应该提前判断并返回空列表，而不是把 -1 传给上层。

**top_k 越界**：请求的 top_k 大于索引中向量总数时，FAISS 会返回填充值。应该把 top_k 钳制到实际数量。

**维度不一致的静默故障**：换过嵌入模型后，旧索引文件的维度与新模型不符。加载时不校验的话，FAISS 会照常工作但返回垃圾结果。应当在加载时校验维度并抛异常，同时提示删除索引重建。
