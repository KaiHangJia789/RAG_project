## 1. 本周补齐的三个硬缺口

Week 9 做出了 chunk 三策略、embedding 客户端、FAISS 封装，但**它们只在一次性脚本里跑通过，从未接入应用主链路**。本周开工前的勘察确认了三个缺口：

| 缺口 | 症状 | 本周处理 |
|---|---|---|
| 向量化链路缺失 | `parse_and_persist()` 写完 chunks 表就结束，从不调用 embedding/FAISS；`data/` 为空，全项目搜不到 `.index` 文件 | 新增 `IndexService` + `DocumentIndexer`，上传后自动入索引 |
| UUID ↔ FAISS id 无桥 | FAISS 要 `int64`，chunks 主键是 `UUID`，表中无任何向量 id 列 | 迁移 005 加 `faiss_id BIGINT` + PG sequence |
| 评测语料不够量级 | `test_docs/` 7 个文件共 2.6KB，撑不起 50 题评测集 | 新建 `data/corpus/` 6 篇共 46KB + 60 题评测集 |

另有两个已查实的约束：**本机 PostgreSQL 18 未安装 pgvector**（`pg_available_extensions` 无 `vector`，004 迁移里的 `ADD COLUMN embedding vector(1536)` 静默失败），所以 FAISS 是唯一可行路线；`EMBEDDING_DIM=1024` 与 SQL 里写死的 `vector(1536)` 的冲突也随之失去意义。

## 2. 关键设计决策

### 2.1 统一切分路径

改造前存在两套切分逻辑：入库走 `ChunkSplitter`（吃 `ContentBlock`，带页码），而 Week 9 的三策略（吃纯文本，无页码）只在脚本里用。这是一处隐患——两者行为不一致，且三策略是死代码。

本周把三策略提升为主路径，按**块类型 + 页码**导向施加：

- **标题、代码块不切分**（切了破坏语义），表格整体保留
- **先按页合并相邻块成一段文本，再对该文本套用切分策略**

第二条是踩了坑才定下来的。最初的实现是「逐块切分，把父块页码继承给子块」，结果四种策略产出**完全相同**的 40 块、均长 62 字、碎片率 45% —— 因为解析器输出的块本身就是段落级的（Markdown 一个自然段一个块），每个都远小于目标长度，策略根本没有发挥空间。改成按页合并后策略才真正在「找边界」。

以页为界是因为**跨页的块无法归属到确定页码**，引用就定位不了。页是硬边界，页内才由策略决定怎么切。

### 2.2 `ParagraphChunker` 的碎片问题

Week 9 的对比表显示 `paragraph` 策略产出 41 个平均 31 字的碎片。原因是它只过滤短段而不合并 —— 这是检索必然失败的量级。

本周加了 `min_chars` / `max_chars` 区间合并。为不破坏 Week 9 的既有测试，**默认 `min_chars=0` 关闭合并**，行为与原来逐字节一致；实验侧显式传 `min_chars=200, max_chars=600`。

效果：

| 策略 | 参数 | 块数 | 均长 |
|---|---|---|---|
| splitter | max_chars=1000, overlap=200 | 33 | 769 |
| sentence | max_chars=1000 | 33 | 664 |
| fixed_size | chunk_size=1000, overlap=200 | 33 | 770 |
| paragraph | min_chars=200, max_chars=600 | 45 | 453 |

`paragraph` 的上限刻意设得比其他策略低：它的设计意图是「尊重段落边界」，若上限也设 1000，短段落会被合并到与 `sentence` 完全相同的粒度，失去对比意义。

### 2.3 检索元数据走 sidecar，不查库

FAISS 的向量命中后需要知道「这段向量对应的原文是什么、来自哪个文件哪一页」。常见做法是回查数据库，本周选择**与索引一起落盘成 `meta.json`**。

这不只是性能考量，更关键的是**可测性**：测试用的 DB 替身对复杂 WHERE / JOIN 支持有限，且匹配失败时会**静默返回全表**（不报错）。在线检索路径只要依赖 SQL 过滤，就等于接受「线上行为无法被单元测试覆盖」。sidecar 方案让检索变成纯内存查找，测试可以完整覆盖。

代价是索引与数据库存在双写，需要一致性自检（见 §6）。

### 2.4 id 分配用 PG sequence，不用应用层计数器

应用层计数器重启后会从 1 重新发号。而 `faiss.IndexIDMap.add_with_ids` **对重复 id 不报错** —— 它只是追加一条新记录。结果是两条不同向量共享同一 id，检索时返回重复 id 挤占 top_k 名额，且回查元数据永远只命中第一个。这是**静默数据损坏，没有任何异常或日志**。

PG sequence 的 `nextval` 天然无此问题（非事务性，回滚会跳号 —— 跳号无害，重号才致命）。写入路径还额外做了 `has_id` 检查作为第二道防线。

## 3. 评估指标定义

> **口径声明**：本章定义本项目的四个核心指标的精确含义与计算方式。这是 v3 计划书明确要求的产出。所有指标由 `app/evaluation/metrics.py` 的纯函数实现，可用单元测试手算校验。

### 3.1 总体约定

1. **判定范围**：`answerable=True` 的题计入质量指标；`answerable=False` 的题**单独统计拒答**，不用忠实度惩罚它（拒答本身不产生幻觉）。
2. **拒答的定义**：检索层拒答（`hits` 为空或全低于阈值）**或**生成层拒答（判官判定 `is_refusal=True`），取二者之一。
3. **判官调用只跑一次**：幻觉率复用忠实度的判定结果，不产生额外 API 调用。
4. **判官与 prompt 版本必须记录**：`PROMPT_VERSION` 参与缓存键，换判官或改 prompt 后历史分数不再可比。

### 3.2 Faithfulness（忠实度）— 断言级连续量

**定义**：答案中能被检索上下文支持的原子断言比例。

**计算方式**（两步法）：
1. 判官把答案拆解为原子断言列表（每条只含一个可独立判断真伪的事实，保留具体数字与条件）
2. 判官**一次调用批量核验**全部断言能否由上下文支持
3. `faithfulness = 被支持断言数 / 断言总数`

**边界处理**：

| 情况 | 取值 | 理由 |
|---|---|---|
| 拒答 | 1.0 | 拒答不含事实断言，天然忠实，不该被惩罚 |
| 零断言且非拒答 | 1.0，标 `degenerate` | 答案没有事实性内容，单独统计该类数量 |
| 判官漏判某条 | 该条按**不支持** | 宁可低估；同时标 `judge_malformed` 并告警 |

**为什么批量核验**：逐条调用的话，8 条断言 = 8 次 API 调用，50 题就是 400 次。批量后每题固定 2 次调用，与断言条数无关。

### 3.3 Answer Relevance（答案相关性）— 问答对级连续量

**定义**：答案对问题的切题程度，**不参考上下文**，因此与忠实度正交。

一段完全忠实于上下文但答非所问的文字，忠实度满分而相关性为零。

**计算方式**：判官按 rubric 直接打分（1.0 完全切题 / 0.7 基本切题 / 0.4 部分相关 / 0.0 完全答非所问）。

**与 RAGAS 原版的偏离（必须声明）**：RAGAS 标准做法是「从答案反推 N 个问题，计算反推问题与原问题的 embedding 余弦相似度均值」。本实现改用判官直评，理由：

- RAGAS 法引入 embedding 噪声（相似度值压缩在 0.5-0.9 的窄带内，绝对数值不可解释）
- 判官直评更直观可解释，便于演示与人工复核

代价是判官直评的方差较大（同一答案重跑可能有 ±0.2 波动）。缓解措施：判官关思考 + 温度 0；报告中记录判官模型与 prompt 版本。`app/evaluation/prompts.py` 里同时保留了反推问题法的 prompt（`relevance_reverse_questions`），可用于交叉验证。

### 3.4 Context Precision（上下文精确率）— 单次检索

**定义**：检索结果的**排序质量**。不只关心「有没有检索到相关片段」，还关心「相关片段是否排在前面」。

**计算方式**（rank-weighted average precision，RAGAS v0.1 口径）：

```
precision@k = (前 k 个位置中相关片段数) / k

ContextPrecision = Σ(precision@k × relevant_k) / 相关片段总数
                       k=1..K
```

分母为零（检索结果全部不相关）时记 **0.0**（不是 NaN）。

**手算校验例子**：相关性序列 `[1, 0, 1, 0, 0]`

| k | relevant | precision@k | 贡献 |
|---|---|---|---|
| 1 | 1 | 1/1 = 1.0 | 1.0 |
| 2 | 0 | 1/2 = 0.5 | 0 |
| 3 | 1 | 2/3 ≈ 0.667 | 0.667 |
| 4 | 0 | 2/4 = 0.5 | 0 |
| 5 | 0 | 2/5 = 0.4 | 0 |

分子 = 1.0 + 0 + 0.667 = 1.667，分母 = 2 → **CP = 0.8333**

这个例子写进了单元测试（`tests/test_evaluation_metrics.py::TestContextPrecision::test_hand_calculated_example`），公式实现不会错。

**与来源版 CP 的区别**：另有一个零 LLM 成本的 `context_precision_source`，只比较「片段所属文档名是否在标注来源集合里」。判官版能识别「同一文档但无关的段落」，来源版不能；但来源版完全确定、零成本。**调参时以来源版为主信号，判官版作旁证** —— 两者结论矛盾时要么判官不可靠，要么标注粒度不够，这个矛盾本身值得深究。

### 3.5 幻觉率（Hallucination Rate）— 答案级二值

**定义**：答案中存在 **≥1 条**无支撑断言即视为「含幻觉」。

```
幻觉率 = 含幻觉的答案数 / 有事实断言的答案总数
```

分母**排除拒答与零断言的答案** —— 这两类不可能有幻觉，计入会稀释指标。

**与忠实度的关系是互补，不是取反**：

| | Faithfulness | 幻觉率 |
|---|---|---|
| 粒度 | 断言级 | 答案级 |
| 类型 | 连续量 | 二值 |
| 受长答案影响 | 被稀释（20 条断言里 1 条无支撑 → 0.95） | 不敏感（同样答案算 100% 含幻觉） |

两个一起看，才能同时掌握**平均质量**与**个体风险**。

**零成本补充：引用有效性（`citation_validity`）**

```
引用有效性 = 有效 [n] 标记数 / 出现的 [n] 标记总数
             有效 = 1 ≤ n ≤ 检索结果条数
```

纯正则、零 API 成本，但能抓到**判官抓不到的幻觉类型** —— 「编造引用编号」。判官只看语义，不看编号是否真实存在。

### 3.6 辅助指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **Hit Rate@K** | top_k 中是否包含任一标注来源文档 | 最直观的召回指标；也是语料质量自检工具 |
| **MRR** | 首个命中标注来源的位置的倒数 | 排序质量，比 Hit Rate 更细 |
| **拒答正确率** | 负样本被正确拒答的比例 | 评估拒答机制 |
| **误拒率** | 可答题被错误拒答的比例 | 拒答不能过度 |

**Hit Rate 的自检价值**：如果 `hit_rate` 很低，问题多半在**语料或标注**，而不在检索代码。这是区分「内容问题」和「代码问题」的第一道分诊。

## 4. 参数调优方法

分三阶段，不做全网格搜索（5 个参数各取 3 个值就是 243 种组合，成本不可承受）：

1. **扫 `final_k`**（3 / 5 / 10 / 20），固定其他参数，观察召回类指标。在某个点之后 recall 饱和而 precision 下降，取拐点。
2. **扫相似度阈值**：画「可回答问题」与「不可回答问题」的相似度分布，取两条分布之间的谷底。
3. **对比切分策略**：在最优 `(final_k, 阈值)` 下比较四种策略。

**阈值绝不能拍脑袋。** 实测本项目的相似度分布：

```
相关问题   top1 ∈ [0.44, 0.73]
无关问题   top1 ≈ 0.30
```

分离带在 0.35-0.40 附近。这个区间与「余弦相似度 0.8 以上才算相关」的直觉相差甚远 —— 不同嵌入模型的相似度分布差异极大，只能从数据里取。默认值 `RAG_MIN_SCORE=0.0`（不过滤）是为了保证 demo 一定能跑通。

## 5. 成本控制

单题约 5 次 LLM 调用：1 次生成 + 2 次忠实度（拆解 + 批量核验）+ 1 次上下文相关性 + 1 次答案相关性。

| 措施 | 效果 |
|---|---|
| 判官**关思考** + 温度 0 | 比降温度对稳定性贡献更大，且快 5-10 倍 |
| 判官**批量判定** | 断言核验与片段判定各 1 次调用，不随条目数增长 |
| **判官缓存**（JSONL） | 改脚本重跑近乎零成本；缓存键含 prompt 版本 |
| **`--limit` 试水** | 先跑 3 题验证链路，再跑全量 |
| **负样本跳过判官** | 负样本只判断拒答，不跑忠实度评估 |
| 评测生成**关思考** | 否则 50 题 × N 配置会跑到天亮 |

## 6. 一致性与可复现

**索引一致性自检**（`build_index.py --verify`）：

```
索引向量数 == SELECT count(*) FROM chunks
              WHERE chunk_strategy = ? AND faiss_id IS NOT NULL
```

**幂等性**：`build_index.py` 重复执行会先删同 `(文档, 策略)` 的旧块再插入，不会撞 `uq_chunks_doc_strategy_index` 约束。

**单一写入路径**：`IndexService.rebuild()` 是全量重建的唯一入口，幂等。`add_records()` 只用于追加新文档，且做了重复 id 检查。

**断点续跑**：`run_rag_eval.py --resume` 跳过已完成的题，**但出错的结果不算完成** —— 否则一次网络抖动会让那道题永远停在错误状态。

## 7. 部署约束

**必须单 worker 运行。** 向量索引是进程内状态，`uvicorn --workers N` 会启动 N 个进程各持一份索引、互相覆盖落盘文件。

```bash
# 正确
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 错误：索引会不一致
python -m uvicorn app.main:app --workers 4
```

要横向扩展需改用 pgvector（需先安装扩展）。

| Answer Relevance | **0.9327** |
| Context Precision（判官版） | **0.8061** |
| Context Precision（来源版，零成本） | **0.9400** |
| Hit Rate | **0.9800** |
| MRR | **0.9700** |
| Citation Validity | **1.0000** |
| 幻觉率 | **4.17%** |
| 拒答正确率 | **100%**（10/10 负样本正确拒答） |
| 误拒率 | 2.00% |
| 平均延迟 | 2611 ms |

### 阈值标定结果

```
可回答问题   (n=50): min=0.402  中位=0.542  max=0.753
不可回答问题 (n=10): min=0.295  中位=0.323  max=0.401

📊 建议阈值: 0.426  →  可答题通过率 96%，不可答题通过率 0%
```

两条分布**完全分离**，中间有一条空旷带（0.401 → 0.402）。这是最理想的情况：一个阈值就能把「该答」和「该拒」干净地分开。

注意这批数值远离「余弦相似度 0.8 以上才算相关」的直觉。不同嵌入模型的分布差异极大，只能从数据里取。

### 语言质量自检的发现

`calibrate_threshold.py` 报告 4 道题的 top1 不是标注来源文档（q004 / q019 / q025 / q040）。这正是自检工具的价值——**它把「内容问题」从「代码问题」里分诊出来**。

抽查这几题的共同点：都是**跨文档综合型问题**（如「Context Precision 怎么算」「参数调优为什么分阶段」），答案在语料中分布在不同文档的相关章节，检索命中了另一篇更相似的文档。这属于**标注粒度问题**而非语料缺失——标注只写了文档名，没写章节，所以只要命中了别的文档就被判为「未命中」。

改进方向：把 `reference_sources` 的粒度从「文档」细化到「章节」，或者在判据里接受「同一主题的相邻文档」。

### 四种 Chunk 策略对比

完整的四策略同批次对比见 `docs/week10/strategy_comparison.md`。要点：

| 指标 | splitter | sentence | fixed_size | paragraph |
|---|:---:|:---:|:---:|:---:|
| Faithfulness | 0.9974 | **1.0000** | 0.9966 | 0.9942 |
| Answer Relevance | 0.9816 | 0.9870 | 0.9816 | **0.9938** |
| Context Precision（判官） | 0.9490 | **0.9674** | 0.9694 | 0.9271 |
| MRR | 0.9517 | 0.9433 | 0.9640 | **0.9800** |
| 幻觉率 | 2.04% | **0.00%** | 2.04% | 4.17% |
| 误拒率 | 2.00% | 8.00% | 2.00% | 4.00% |

三个结论：

1. **切分策略对生成质量影响有限**（判官指标差异 < 5%）。结构清晰的技术文档语料上，模型能从不同切分粒度提取相近语义 —— 不必在切分上过度优化。
2. **paragraph 检索排序最好**（MRR 0.980、source precision 0.472），因为块边界与文档结构对齐。
3. **误拒率是最该优先解决的问题**：所有策略都有 2-8% 误拒，根因是生成层拒答过严 + 检索 top 块未命中答案（无 overlap 的 sentence 在边界题上更脆弱，误拒 4 道）。

### 评测过程中发现的两个方法论问题

**判官批次漂移**：sentence 首次评测（9-13）与另外三策略（9-15）相比，判官指标明显偏低；同批次重跑后恢复。**对比不同配置必须同批次跑完**，否则会把判官漂移误读成配置差异。

**Hit Rate / MRR 语义修正**：初版用「答案引用的文档」而非「检索命中的文档」计算检索指标，混入了 LLM 是否引用这个变量。已修正为 `RagAnswer.retrieved_docs`。

## 10. 已知限制

1. **单 worker**（见 §7）。
2. **索引与 DB 双写**：DB 提交成功但 FAISS 写入失败时会留下「有记录无向量」的不一致。这是**良性可检测故障** —— 检索查不到就跳过，`build_index.py` 一条命令修复。反过来（先写 FAISS 后写 DB）会产生悬空指针，只能全量重建，所以选了前者。
3. **`SentenceChunker` 的 `start`/`end` 不对应原文偏移**：跨块拼接后没有全局偏移的概念，定位靠 `page_number` + `chunk_index`。若后续要做「高亮原文片段」需先修这个。
4. **判官稳定性**：LLM-as-Judge 的固有风险。缓解措施见 §5，但更换判官模型或修改 prompt 后历史分数不可比。
5. **chunks 表的 `embedding vector(1536)` 死列**：004 迁移遗留，本机无 pgvector 所以该列从未创建。走 FAISS 路线后这列无意义，未做清理。
